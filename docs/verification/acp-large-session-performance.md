# ACP 大会话性能对比（R13）

日期：2026-11-28。对比对象：0.4.185 基线（`7aa6b5d0`），以及改动后的版本（在 `79bb7108` 的 T1–T7 之上加入 T6 的未提交工作区，即时间线虚拟化、增量分段、行组件 memo、渲染缓存和流式 Markdown 节流）。这部分工作随后提交为 `7b840b35`。

0.4.186、0.4.187 已由外部进程发布；本文基线仍为 0.4.185（7aa6b5d0）。

> **范围说明**：本文数据来自浏览器预览（`vite preview`）加 `scripts/capture-workbench.mjs` 的合成 IPC，在 Playwright Chromium（headless shell，Playwright 1.63.0）中测得。它不能代替原生应用（WebView2）的 CPU 和内存验收，也不能代替长时间泄漏验收；原生平台行为仍未验证。

## 环境与方法

- 机器：Intel Core i7-9700F（8 核）、32 GB 内存、Windows 11、Node.js v26.4.0。两个版本在同一台机器上依次测量，测量期间不运行其他测试。
- 基线构建：用临时 worktree 检出 `7aa6b5d0`，路径为 `%TEMP%\cliora-baseline-0.4.185`。在其中执行 `npm ci` 和 `vite build`。这里跳过了 `tsc -b`，因为临时目录的上级目录中有一份无关的 `@types/node`，会让类型检查报错；`tsc` 不产生构建产物，所以跳过它不影响产物。然后在 14792 端口执行 `vite preview`。基线代码没有任何改动。
- 改动后构建：在主仓库执行 `npm run build`，然后在 14791 端口执行 `vite preview`。
- 两边使用同一个测量脚本，也就是改动后仓库中的 `scripts/capture-workbench.mjs`：
  `CLIORA_PREVIEW_URL=<预览地址> CLIORA_CAPTURE_OUT=<临时目录> node scripts/capture-workbench.mjs --only "workbench-acp-large-perf*" --performance --theme light`
- 合成场景 `workbench-acp-large-perf`（1×）和 `-2x`（2×）：
  - 大会话 `acp1` 分别有 600 轮和 1200 轮已结束的对话，约 1M 和 2M 字符，3002 和 6002 个条目。每轮包含：一条用户消息、一段思考、一个带文本输出的 execute 工具、一段 Markdown 回复（含列表和表格，每 4 轮含一个 ts 代码块）和一个轮次结束。末尾是一轮进行中的对话，回复 `live` 正在流式输出。
  - 两个小会话 `acp2`、`acp3` 同时在后台流式输出。加载时选中的是 `acp2`，大会话一开始处于隐藏状态。
  - 合成宿主在 `acp_close` 后删除该会话，与原生宿主一致，所以关闭后的堆只反映前端自己还持有的内存。
- 测量步骤：
  1. **加载后**：做两次 `HeapProfiler.collectGarbage`，然后读取 `JSHeapUsedSize`、`Memory.getDOMCounters`，以及 `acp1` 中带 `data-item-id` 的条目数。
  2. **切换到大会话的首次渲染时间**：从点击 `acp1` 的标签开始计时，到 `live` 条目完成布局并出现在视口内、再过一帧为止。
  3. **显示后**：与第 1 步读取的指标相同。
  4. **流式输出**：固定工作量，共 200 组，每组给 `acp1`、`acp2`、`acp3` 各发一个 chunk，组间隔 16 ms（页面跟得上时约为每秒 60 组）。用 `PerformanceObserver('longtask')` 记录长任务的数量、最长时长和总时长，同时记录实际耗时和事件吞吐。
  5. **关闭后**：点「结束此会话」并确认，等 `acp1` 的窗格卸载，再按第 1 步读取指标。
- 改动后版本测了 3 轮，下表取中位数；基线每轮需要约 17 分钟，测了 1 轮，作为佐证的另一轮放在后面单独说明。

在同一台机器上，有一段时间另一个外部进程在做发布相关的 git 和 npm 操作。那段时间里，按时间驱动的旧工作量测量改动后版本，出现过 0–13 个超过 50 ms 的长任务，最长 129 ms。逐帧 trace 显示，这些长任务由一帧中的 Markdown 解析、垃圾回收和布局叠加而成。为此加入了流式 Markdown 节流（见下文）。上表是机器空闲时的最终结果，3 轮都没有长任务。

## 全量渲染阈值对 DOM 的影响

时间线只有在分段数超过 `FULL_RENDER_MAX_SEGMENTS = 80`（`AcpTimeline.tsx`）时才虚拟化：

- **阈值以下**（≤ 80 段）：每一段都渲染，DOM 随条目数**线性**增长。短对话保留完整的 DOM 和无障碍树，现有用例也按这个行为断言。
- **阈值以上**：只渲染视口内的分段，再加上两侧各 6 段的 overscan，以及持有键盘焦点的那一段。DOM **基本恒定**，与对话长度无关：上表中 3002 和 6002 个条目时都是 10 个条目、1 717 个节点。
- 隐藏窗格不受阈值影响，一律不渲染列表。
- `tests/ui/workbench-acp-large.spec.ts` 用 1000 段和 2000 段的会话验证 DOM 行数基本不变，并有一个从 79 段增长到 87 段、跨过阈值的用例，验证跨越时阅读位置不跳、展开状态不丢。

## 改动后版本做了什么

- `@tanstack/react-virtual` 3.14.28 对分段做动态高度虚拟化。行高按实际布局测量，不取整，避免误差逐行累积。行高变化时由虚拟器修正滚动位置，并关闭浏览器自带的 `overflow-anchor`，防止重复修正。正在跟随最新输出时，不修正滚动位置，由跟随观察器保持在底部。查找和定位的目标如果不在 DOM 中，先滚动到所在分段，渲染出来后再精确定位和聚焦。
- `createSegmentBuilder`：最后一轮之前的分段只在其中的条目对象变化时才重建，未变化的分段沿用旧对象。
- 行组件（`SegmentRow`、`AcpMessage`、`AcpToolCard`、`AcpStep`、`AcpProcess`、`AcpStartupGroup`、`AcpToolGroup`、`AcpCodeBlock`）都用了 memo。传给行的回调保持同一个引用，传给行的 snapshot 也只在行实际读取的字段变化时才更新。
- `acpRenderCache.ts`：按会话保存展开状态、阅读锚点和代码高亮结果，关闭会话（store 的 `retire`）时一并清除。
- 回复流式输出期间，Markdown 最多每 100 ms 重新解析一次（`STREAMING_MARKDOWN_MS`）；输出结束后立即显示全文。
- Markdown 结果的缓存只做到「内容不变时不重新渲染」，即对 `MarkdownView` 做 memo。分段滚出范围后重新挂载时仍会重新解析，因为 `MarkdownView`（`src/components`）不在本任务范围内。
