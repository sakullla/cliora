# ACP 大会话性能对比（R13）

日期：2026-11-28。对比对象：0.4.185 基线（`7aa6b5d0`），以及改动后的版本 `ad225d90`（合成场景补充 diff 和终端输出，打开的工具详情不再随其他终端的输出重绘）。时间线虚拟化、增量分段、行组件 memo、渲染缓存和流式 Markdown 节流这几项已在 `7b840b35` 提交。

0.4.186、0.4.187 由外部进程发布，本文的基线仍是 0.4.185（`7aa6b5d0`）。上一版记录使用的场景没有 diff 和终端输出，字符数也写错了（见文末「对上一版记录的更正」）。本文的数据全部按新场景重新测量。

> **范围说明**：本文数据来自浏览器预览（`vite preview`）加 `scripts/capture-workbench.mjs` 的合成 IPC，在 Playwright Chromium（headless shell，Playwright 1.63.0）中测得。它不能代替原生应用（WebView2）的 CPU 和内存验收，也不能代替长时间泄漏验收。原生平台行为仍未验证。

## 环境与方法

- 机器：Intel Core i7-9700F（8 核）、32 GB 内存、Windows 11、Node.js v26.4.0。两个版本在同一台机器上测量，测量时不运行其他测试。不过机器上一直有一个与本测量无关的 WebView2 进程在占用 CPU（采样时整机负载约 39%），见「长任务」一节。
- 基线构建：用临时 worktree 检出 `7aa6b5d0`，路径为 `%TEMP%\cliora-baseline-0.4.185`。在其中执行 `npm ci` 和 `vite build`，然后在 14792 端口执行 `vite preview`。这里没有执行 `tsc -b`，因为 `tsc` 不产生构建产物。基线代码没有任何改动。
- 改动后构建：在主仓库执行 `npm run build`，然后在 14791 端口执行 `vite preview`。
- 两边使用同一个测量脚本，也就是改动后仓库中的 `scripts/capture-workbench.mjs`：
  `CLIORA_PREVIEW_URL=<预览地址> CLIORA_CAPTURE_OUT=<临时目录> node scripts/capture-workbench.mjs --only "workbench-acp-large-perf*" --performance --theme light`
- 合成场景：

  | 场景 | 已结束的轮次 | 条目 | 宿主计数的字符数 | 保留的终端 | 标为已省略的终端 |
  | --- | ---: | ---: | ---: | ---: | ---: |
  | `workbench-acp-large-perf-ref`（参照） | 0 | 4 | 796 | 1 | 0 |
  | `workbench-acp-large-perf`（1×） | 600 | 4 204 | 959 032 | 33 | 568 |
  | `workbench-acp-large-perf-2x`（2×） | 1 200 | 8 404 | 1 923 209 | 33 | 1 024 |

  - 字符数按宿主的计法统计：`src-tauri/src/acp/timeline.rs` 中的 `weight()` 按 Unicode 字符（`chars().count()`）累加消息正文、工具标题、`rawInput`、文本和 diff 内容以及位置路径。脚本中的 `hostTimelineChars` 复制了这个计法，每次测量时把结果写进 manifest。2× 场景是宿主时间线上限 `MAX_TIMELINE_CHARS = 2 000 000` 的 96%。宿主超过上限时会把时间线裁到 75%，所以真实会话保留的时间线不会比它大很多。
  - 每轮 7 个条目：一条用户消息、一段思考、一个带文本输出的 execute、一个带 diff 的 edit（CSS，约 13 行改为 15 行）、一个输出在终端里的 execute（`terminal` 内容）、一段 Markdown 回复（含列表和表格，每 4 轮含一个 ts 代码块），以及轮次结束。
  - 终端按宿主的保留规则合成：最近 32 个已结束的终端带完整输出（约 10 行构建日志，退出码 0），更早的终端 ID 放进 `omittedTerminalIds`，最多 1024 个（`MAX_RELEASED = 32`、`MAX_OMITTED = 1024`）。终端输出不计入时间线的字符预算，宿主对它另有上限。
  - 末尾是一轮进行中的对话：一个带 diff 的 edit、一个仍在运行的 execute（终端 `term-live`），以及正在流式输出的回复 `live`。
  - 参照场景只有这一轮进行中的对话，用作「打开大会话之前」的堆参照。
  - 两个小会话 `acp2`、`acp3` 同时在后台流式输出。加载时选中的是 `acp2`，大会话一开始处于隐藏状态。
  - 合成宿主在 `acp_close` 后删除该会话，这一点与原生宿主一致。所以关闭后的堆只反映前端自己还持有的内存。
- 测量步骤：
  1. **加载后**：做两次 `HeapProfiler.collectGarbage`，然后读取 `JSHeapUsedSize`、`Memory.getDOMCounters`，以及 `acp1` 中带 `data-item-id` 的条目数。
  2. **切换到大会话的首次渲染时间**：从点击 `acp1` 的标签开始计时，到 `live` 条目完成布局并出现在视口内、再过一帧为止。
  3. **打开 diff 和终端**：像读者查看时那样，展开进行中这一轮的 edit 和 execute（已经展开的保持不变），等到 diff 行出现。两个版本都确认显示了 20 行 diff 和终端输出（manifest 中的 `openedBodies`）。
  4. **显示后**：读取与第 1 步相同的指标。
  5. **流式输出**：固定工作量，共 200 组。每组给 `acp1` 发一个回复 chunk 和一行终端输出（`terminalOutput`），再给 `acp2`、`acp3` 各发一个 chunk，共 800 个事件。组间隔 16 ms，页面跟得上时约为每秒 60 组。用 `PerformanceObserver('longtask')` 记录长任务的数量、最长时长和总时长，同时记录实际耗时和事件吞吐。
  6. **关闭后**：点「结束此会话」并确认，等 `acp1` 的窗格卸载，再读取与第 1 步相同的指标。
- 改动后版本测了 5 轮，下表取中位数，括号内是 5 轮的范围。基线一轮约 22 分钟，完整测了 1 轮。第 2 轮的参照和 1× 场景与第 1 轮一致，2× 场景在点击时超时（30 s），没有得到数据，原因是基线页面在 2× 下长时间无响应。

### 长任务

需求的目标是改动后流式期间没有超过 50 ms 的长任务。在这次测量中没有达到：改动后版本每轮仍有 0–11 个，最长 124 ms。有三点说明它们与对话的长度无关：

- 只有 4 个条目的参照场景也有长任务（5 轮中 4 轮出现，最长 78 ms）。
- 在同一段时间里交替测量两个版本的参照场景，基线也出现了长任务（7 轮中 3 轮出现，最长 88 ms）。同一工作量下主线程的任务总时长（CDP `TaskDuration`）改动后为 3.5–5.0 s，基线为 4.5–5.6 s。
- 1× 和 2× 的条目数相差一倍，长任务的数量和时长却在同一范围内。基线在 1× 和 2× 下各有约 600 个长任务，几乎每组事件都会触发一个，最长的达到 10 s。

CPU 采样显示，剩下的每帧开销主要来自 `AcpComposer` 和其中的 `PromptPicker`（每个事件都重新渲染）、终端输出视图（每行输出都要重新渲染并滚动到底部），以及时间线最后一段。前两者不在 T6 范围内。机器上另有进程在占用 CPU（见「环境与方法」），这时一帧中的渲染、GC 和布局叠加起来就会超过 50 ms。上一版记录中机器空闲时的 3 轮都是 0，但那次的场景没有终端输出流。

**偏差（用户已接受，2026-11-28）**：R13 「流式期间没有超过 50 ms 的长任务」这一项本期未达到，用户确认接受。大会话本身的长任务已从约 600 个（最长数秒）降到个位数（最长 124 ms）。后续可做：`AcpComposer`/`PromptPicker` 避免随每个事件重渲染，终端输出按帧合并，并在空闲机器上重测。另需注意，测量期间那个占用 CPU 的 WebView2 进程是本机运行的 Cliora 桌面版，其后台终端的开销由 R16（`2387fc58`）修复。

本次测量还发现并修正了一个问题：展开的 diff 会随**其他**终端的每一行输出重新计算。原因是工具详情读取整个 snapshot，而任何终端输出都会产生新的 snapshot。现在 `AcpStep` 和 `AcpToolCard` 中的详情用 `toolBodyPropsEqual`（`acpRenderCache.ts`）做 memo，只有详情实际读取的内容变化时才重绘，包括会话是否存活、目录、本调用自己的终端及其是否被省略。修正前，在一次 CPU 采样中，diff 计算和 diff 行渲染占了 0.5 s 以上；修正后，它们不再出现在采样结果里。

### 关闭会话后的堆

- 参照场景从没有打开过大会话，关闭进行中的会话后，堆从加载后的 10.2 MB 升到 12.4 MB，两个版本都是这样。所以关闭后比加载后高约 2 MB，与对话长度无关。这部分是窗格显示过一次之后留下的东西：首次执行时加载的模块和编译出的代码、窗格和对话框用到的翻译与状态。会话数据本身不在其中，合成宿主已经删掉了它。
- 改动后 1× 和 2× 的关闭后堆是 13.4 MB 和 13.3 MB，比参照场景高约 1 MB，而且条目翻倍后没有增加。多出来的这部分来自大场景才会执行的代码路径，比如 Markdown 表格、代码高亮和虚拟列表，并不随数据量增长。DOM 节点（1 320 比 1 318）和事件监听器（729）回到了参照场景的水平。
- 基线的关闭后堆随场景变大：参照 12.4 MB，1× 14.3 MB，2× 15.1 MB。
- 以上是浏览器中 GC 后的读数，不能代替原生 WebView2 的长时间泄漏验收。

## 功能回归

`tests/ui/workbench-acp-large.spec.ts` 在合成宿主上用 1000 段和 2000 段的会话验证以下行为。本次改动后全部通过：

- 条目数翻倍时，渲染的行数基本不变；隐藏窗格不渲染行（`the rendered rows stay about the same …`）。
- 查找最早一条消息中的文字时，能跳到那条消息并高亮（`finding text in the earliest message …`）。
- 定位到位于顶部、尚未渲染的待处理授权卡，并能用键盘回答（`locating a waiting card at the top …`）。
- 向上阅读时流式输出不打断阅读，「回到最新」之后重新跟随（`reading back is not interrupted by streaming …`）。
- 展开或收起视口上方的分段时，阅读位置保持不变（`opening or folding a segment above the viewport …`）。
- 隐藏窗格再显示时，阅读位置和展开的分段都能恢复（`a hidden pane comes back …`）。
- 分段数从 79 增长到 87、跨过全量渲染阈值时，阅读位置和展开状态都保持不变（`growing past the full-render limit …`）。

## 全量渲染阈值对 DOM 的影响

时间线只有在分段数超过 `FULL_RENDER_MAX_SEGMENTS = 80`（见 `AcpTimeline.tsx`）时才虚拟化：

- **阈值以下**（≤ 80 段）：所有分段都渲染，DOM 随条目数**线性**增长。短对话因此保留完整的 DOM 和无障碍树，现有用例也按这一行为断言。
- **阈值以上**：只渲染视口内的分段，加上两侧各 6 段的 overscan，以及持有键盘焦点的那一段。DOM **基本恒定**，与对话长度无关。上表中 4 204 和 8 404 个条目时，都只渲染了 8 个条目、1 898 个节点。
- 隐藏窗格不受阈值影响，一律不渲染列表。

## 改动后版本做了什么

- 用 `@tanstack/react-virtual` 3.14.28 对分段做动态高度虚拟化。行高按实际布局测量，不取整，这样误差不会逐行累积。行高变化时由虚拟器修正滚动位置，同时关闭浏览器自带的 `overflow-anchor`，避免两边重复修正。正在跟随最新输出时不修正滚动位置，由跟随观察器保持在底部。查找或定位的目标不在 DOM 中时，先滚动到它所在的分段，等分段渲染出来，再精确定位和聚焦。
- `createSegmentBuilder`：最后一轮之前的分段，只有其中的条目对象变化时才重建，未变化的分段沿用原来的对象。
- 行组件（`SegmentRow`、`AcpMessage`、`AcpToolCard`、`AcpStep`、`AcpProcess`、`AcpStartupGroup`、`AcpToolGroup`、`AcpCodeBlock`）都用了 memo。传给行的回调保持同一个引用。传给行的 snapshot 只在行实际读取的字段变化时更新。展开的工具详情还要再判断一次，只有详情实际读取的内容变化时才重绘（`toolBodyPropsEqual`）。
- `acpRenderCache.ts`：按会话保存展开状态、阅读锚点和代码高亮结果，关闭会话（store 的 `retire`）时一并清除。
- 回复流式输出期间，Markdown 最多每 100 ms 重新解析一次（`STREAMING_MARKDOWN_MS`）。输出结束后立即显示全文。
- Markdown 的结果只缓存到「内容不变时不重新渲染」这一步，也就是对 `MarkdownView` 做 memo。分段滚出范围后重新挂载时，仍会重新解析，因为 `MarkdownView` 在 `src/components` 中，不在本任务范围内。

## 对上一版记录的更正

- 上一版写的是「约 1M 和 2M 字符」，这是 UTF-8 字节数。按宿主的计法，那两个场景只有约 59 万和 119 万字符，是上限的 30% 和 60%。新场景按宿主计法统计，2× 场景约为上限的 96%。
- 上一版的场景没有 diff 和终端输出，因此没有覆盖这两条渲染路径。新场景每轮都有 diff 和终端，测量时会展开进行中这一轮的 diff 和终端，并向终端流式输出。
- 上一版没有给出打开大会话之前的堆参照。新场景加入了参照场景。
