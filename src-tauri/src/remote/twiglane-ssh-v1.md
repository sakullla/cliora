# Twiglane remote connection interface v1

Cliora's installed native executable recognizes `--twiglane-remote-v1` before desktop startup. A caller starts the executable directly with piped standard streams. These calls work when the desktop is closed and do not acquire its single-instance lock. Use the installation that owns the user's Cliora configuration. On macOS the bundle identifier is `com.cliora.desktop`; locate the bundle executable through its Info.plist. The executable name on Linux and Windows is `cliora` and `cliora.exe` respectively.

All arguments below follow that flag. A successful local response is one UTF-8 JSON line. Local errors exit 2 and write `{"error":"code"}` to stderr. In SSH mode stdout belongs exclusively to the remote operation. SSH failures exit with the SSH status, usually 255 on transport uncertainty. Treat stderr as diagnostic data and redact it before displaying or recording it.

| Arguments | Standard streams and result |
|---|---|
| `version` | Returns `{"protocol":1,"kind":"cliora-twiglane-connector-v1"}`. No database needed. |
| `list` | Returns `{"protocol":1,"targets":[...],"unavailable":[...]}`. An unreadable or ambiguous SSH configuration leaves that target in `unavailable` with its ID, name and error. Each enabled target contains `targetId`, opaque string `targetRevision`, `name`, `host`, `user`, numeric `port`, resolved `effectiveHost`, `authMethod` and nullable `defaultPath`. |
| `probe ID CATALOG_REVISION` | Reads the current target and connects over SSH. Returns `system`, `architecture`, `pythonVersion`, `agentSha256` (null if missing), and the authenticated `peerRevision`. No directory or file is created on the remote host. A missing Python 3 interpreter is reported by SSH. |
| `install ID PEER_REVISION SHA256 SIGNATURE` | Caller must obtain installation confirmation. Stream the exact agent artifact on stdin and close stdin. Stdout emits JSON lines with cumulative `receivedBytes` from the **remote** receiver, ending with `{"installed":true,"agentSha256":"..."}` only after successful verification and atomic replacement. Maximum agent size is 8 MiB. |
| `connect ID PEER_REVISION SHA256 SIGNATURE` | Verifies the signature locally and digest remotely, then binds stdin/stdout to the no-argument agent. Agent request and response frames are defined by Twiglane. Closing stdin permits normal shutdown. When cancelling, close the pipes and terminate the owned process tree. A disconnected write needs its operation ID to confirm its outcome. |

Cliora opens its existing database read-only, requires SSH enabled globally, drops disabled targets from the list, and reloads the target for each SSH action. A changed revision yields `target_changed`; an absent/disabled target yields `target_unavailable`. Never substitute another target by name or path. The revision covers the saved target, credential edits, and the effective OpenSSH configuration resolved with `ssh -G`, including HostName, host-key lookup, authentication paths and proxy or jump profiles. A transient private snapshot supplies the configuration to SSH for the operation; an edit to an alias or included file after the revision check cannot redirect the upload. The caller owns the helper and SSH process tree during cancellation. Only renaming the display label preserves revision. For quoted trust filenames, the helper reads the consulted SSH configuration directives and asks OpenSSH to expand the operands with explicit separators. The catalog revision incorporates the content and availability of user/global known-hosts and revocation files, including those of jump hosts. Each transport reads private snapshots of the trust material used for its revision.

An existing saved password is handled by Cliora's normal credential backend and askpass helper. To collect a missing password or key passphrase for one connection, Twiglane can supply an absolute native `SSH_ASKPASS` executable and `SSH_ASKPASS_REQUIRE=force`. Only its local private reply pipe carries an entered secret. Its prompt must handle cancellation and must not answer host-key questions. A password target without either path yields `password_required`. With key auth and no prompt helper, the tool uses batch mode. The configured known-hosts verification, identity files and proxy remain in force.

The installation target is fixed to `~/.local/share/twiglane/agent/v1/agent`, owned by the SSH account. The remote bootstrap checks owner, file type and write permissions, then writes to a private temporary file in that directory. A checksum mismatch or short upload cannot replace an existing agent. `connect` loads the fixed file, verifies its checksum, and starts that exact Python source in the isolated interpreter. Replacing the file during connection cannot substitute unverified code. The remote account needs Python 3 on PATH.

The case-sensitive SHA256 argument is a 64-character lowercase SHA-256 hex digest. Sign the exact UTF-8 bytes `twiglane-agent-v1 sha256:<digest>\n` (one terminating LF) using Twiglane's Tauri updater key. SIGNATURE is the base64 text emitted in the Tauri signer .sig file, trimmed. Binding the artifact type into the signed message prevents the signature of another updater artifact authorizing an install. Package the verified agent and this detached signature with the Twiglane desktop release. Updating the publisher key requires coordination.

Development builds alone accept the literal signature `development` for a digest matching the sibling Twiglane checkout's `remote-agent/agent`. These builds can read an isolated fully qualified database path from `CLIORA_TWIGLANE_TEST_DB`. Release builds always require a publisher signature and use the installed desktop database.

For compatible-version reuse, probe also returns `agentSignature` saved during verified installation. Pass the installed digest/signature pair to connect. Cliora verifies the publisher and exact previously installed bytes again. A successful v1 agent handshake permits reuse when the installed digest differs from the bundled version. Missing or invalid proof and incompatible handshakes require a fresh confirmed installation. A development proof is valid only for the exact current development tree.

Use the stable 64-character lowercase hex `targetRevision` from list to probe the selected catalog entry. Only after the probe has succeeded, retain its 64-character `peerRevision` with the host shown to the user. Pass that peer revision, unchanged, in the revision position of install and connect. It binds the catalog revision plus the public keys from the actual OpenSSH host key exchanges, including ProxyJump hops. OpenSSH still enforces its normal trust checks and any configured KnownHostsCommand. The helper contributes no additional trusted keys. The peer proof has no wall-clock expiry or persistent credential state. A different peer, route, or trust material requires a fresh probe and confirmation. A catalog revision by itself yields `probe_required` for install/connect. When retrying an installation already displayed for confirmation, retain the original peer proof until the user makes a fresh selection.
